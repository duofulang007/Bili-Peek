# 分片下载试验记录 · 2026-10-04

状态：0.3.31 的可选原型已实现，原有下载方式仍为默认。用户确认 0.3.30 提速明显，同时反馈速率波动；0.3.31 的音视频并行尚需真实页面速度对照。此前的[调查记录](clip-download-research-2026-10-04.md)属于实现前的证据，不是当前能力清单。

## 接入方式

网页传入当前画质轨道的 SegmentBase 初始化范围和索引范围。助手解析 SIDX v0/v1，按轨道各自的 presentation origin 选择覆盖用户时间区间的分片；起点向前扩到可独立解码的 SAP，保留可变分片时长。嵌套索引和不支持的边界明确拒绝。

助手生成仅含已选分片的本地 HLS 清单。锁定版本 N_m3u8DL-RE 负责四并发与有限重试；现有 18766 监听器通过随机临时路由执行严格 HTTPS/206/Content-Range 校验，计数实际网络字节并缓存完整分片。此桥接未要求 RE 的 SegmentBase 分支自行展开 SIDX，也不解析终端进度输出。临时路由只接受持有随机路径的本机 GET，不接受页面 Origin，不暴露远程地址。助手其余 API 继续要求配对码。

最终按原时间戳组装初始化段与媒体分片，FFmpeg 使用各轨道原点补偿后精确重编码裁剪。现有音视频轨道、时长及完整解码核验保留。实际工具固定为[官方 v0.6.0-beta](https://github.com/nilaoda/N_m3u8DL-RE/releases/tag/v0.6.0-beta) 的 Windows x64 20260629 包，安装脚本核对官方包 SHA-256。

## 已验证

- 完整语法检查及 52 项 Node 回归测试通过，无跳过。已有配对、用户数据、字幕、导出、加载器回归保留。
- 使用实际 FFmpeg 生成 12 秒的独立 H.264/AAC fMP4，下载 5.1–7.4 秒非关键帧选区，实际 RE 读取本地清单并调度下载。输出 2.341333 秒，通过完整解码；首帧和解码后的第一秒音频逐字节匹配原方式的裁剪成品。
- 下载中实际结束 RE 进程并暂停，1.5 秒后重新启动继续；暂停期间速率为零。重试同一区间只读取两轨道的初始化段和索引，缓存媒体不重复请求。相同大小的缓存内容损坏会被 SHA-256 检出，仅重新下载损坏分片。
- 正确处理 SIDX v0/v1 与可变时长；截断/嵌套索引、错误范围和整文件 HTTP 200 返回明确失败。持续推进的进程可以超过无进展时限，停滞与取消均终止进程。
- 65 项本地页面验收通过，涵盖进度、字节/速率、暂停/继续、取消、默认方式、草稿重试，以及原有双图和定位行为；0.3.29 使用 Edge，0.3.30 在应用内浏览器复测通过。此处助手响应是模拟数据，不能代替真实下载验证。

## 并发测量

在同一媒体、同一区间、冷缓存下，将每个上游请求限制为每 120ms 返回 4096 字节；交错测试单并发与四并发各两次，不包含暂停。两种配置实际接收字节均为 164098。

| 并发度 | 第一次 | 第二次 | 平均 |
| --- | --- | --- | --- |
| 1 | 5.899 秒 | 5.901 秒 | 5.900 秒 |
| 4 | 3.376 秒 | 3.400 秒 | 3.388 秒 |

该模拟条件下四并发用时减少约 43%，证明调度桥接能利用每连接带宽。它不是 B 站限流模型，也不是与原 FFmpeg 网络下载的速度比较。原方式测试读取本地完整源，0.12 秒的处理耗时不能与模拟限速下载直接比较。选中的初始化段与媒体共 163874 字节；全源两轨道 480015 字节，该比例也不能直接当作原方式的带宽节省，因为原方式本来就可能使用 Range。

上表为 0.3.29 的历史测量。0.3.31 的复测命令改为串行/并行交错对照：`$env:BILI_PEEK_SEGMENT_BENCHMARK='1'; node --test tests/segment-download.test.cjs`。报告生成在忽略的 `.local/segment-prototype-test.json`，普通回归会覆盖报告；本文保存实际测量。浏览器预览的 `?download-demo=1` 仅供模拟控件检查，不写真实笔记。

## 0.3.31 并行对照

保持同一实际 RE、同一生成媒体和选区、每请求每 120ms 返回 4096 字节、冷缓存与无暂停。交错顺序为串行、并行、并行、串行；每次实际收到 164098 字节，组装后的两轨道均逐字节一致。

| 调度 | 第一次下载阶段 | 第二次下载阶段 | 平均 |
| --- | --- | --- | --- |
| 视频/音频串行，各四连接 | 3.390 秒 | 3.393 秒 | 3.392 秒 |
| 视频四连接、音频单连接同时下载 | 2.701 秒 | 2.700 秒 | 2.701 秒 |

此可控条件下下载阶段用时约减少 20%；排除准备后，传输部分平均从 2.885 秒降至 2.190 秒。并行不是任意网络下都更快：总带宽受限时仍会竞争，真实 CDN 的波动无法由此测量推断。实际引擎回归另覆盖双轨道暂停/继续，以及音频失败时停止视频并清理临时路由。

速率显示改为近三秒平均，瞬时速率仍由实际接收量计算，不能将显示更平稳当成网络提速。新增日志区分准备、传输、组装和单轨道用时，以便下一条真实任务确认尾段等待、无数据时段或媒体处理是否主导耗时。完整缓存跳过下载器启动。

## 当前边界

0.3.30 接收当前画质轨道的最多三个合法主备地址。先核对初始化段和索引，再对同一媒体范围最多读取 1 MiB 测速并核对内容，单次请求最多 8 秒；选中较快的来源。缓存完整命中时省略测速，测速和失败请求实际收到的字节计入总接收量。失败时后续重试切换同轨道来源；分片完成后持续速率明显不足时切换后续分片，保留已经下载的内容。慢源判定考虑并发连接对带宽的分摊，切换不会中断仍在推进的请求。

实际 RE 回归覆盖了快速备源下载失败后回退，以及主源下载变慢后切换后续分片，两次输出均与原成品逐字节一致。记录只包含来源域名、候选数和切换次数，不保存签名地址。测试来源使用本地生成媒体及可控响应，不能据此承诺真实 CDN 的提速比例。

暂停只覆盖下载阶段，复用完整分片，未完成分片重取；不保证分片内部断点续传。取消或重启后需要页面重新提交，未实现持久任务队列和自动继续。缓存按源初始化段、索引、选中分片、视频与轨道身份区分，未实现重叠选区之间的共享缓存、容量限制或自动回收。

尚需真实 B 站验证：登录页面是否提供索引、CDN Range、不同编码、长任务中后段、接近源末尾、签名过期、限流与磁盘不足；以及冷缓存交错重复的原方式/分片方式对照。没有这些证据前不替换默认下载方式，也不宣称实际崩溃问题已全部消除。
