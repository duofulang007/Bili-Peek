# 0.3.35 多视频保存与统一进度条

原助手用单个 active key 拒绝第二项任务；页面也用全局 exportingRoute 锁住保存按钮。现在最多两个不同视频或分 P 同时保存，超出容量的任务排队；相同 id/cid 的选区等待前一项，避免共享分片缓存出现双写。提交重复活动任务返回原 key。排队可单独取消，运行中的暂停、继续和取消仍使用对应任务的 TransferControl。健康接口保留 active 布尔值，并返回 activeCount 与 queuedCount；更新/停止保护仍覆盖所有运行和等待任务。

每个分片任务保持现有视频四连接、大音频双连接的限制，两个任务最多十二个媒体请求。本次解除了任务级串行限制，没有盲目增加单视频连接数。同名笔记在最终独占提交发生碰撞时追加任务短编号，结果中的笔记路径和 Obsidian 链接同步调整。临时媒体目录仍各自独立。

页面改为按视频路由记录保存状态。当前视频正在保存时阻止重复提交，切换其他视频后仍可保存；旧任务继续轮询，不能改写新视频的进度。返回原视频恢复自己的进度。准备、排队、下载、裁剪、核验和最终结果复用同一个 progress 元素，数值不倒退；完成、取消、失败保留原控件，终态隐藏操作。阶段和最终结果集中用旁边的文字描述。

## 验证

- 实际本机 HTTP 队列回归先返回 409，改动后同时启动两项并返回 202。覆盖第三项等待、排队取消、重复提交、暂停隔离、空位自动接续、同视频缓存写入串行和健康计数。
- 完整 60 项 Node 回归通过，无跳过。实际 FFmpeg 本地媒体回归同时保存两个同名视频，笔记路径不同且各自引用正确附件。
- 76 项浏览器模拟助手验收通过，覆盖单一 progress 元素从准备到终态的身份保持、排队文字、下载中切换路由仍可保存和返回后恢复原进度；这不代表真实 B 站已安装副本的验收。

## 下载源小范围观察

用户提供 BV1aJ7rzaE9C，公开接口仅能取得 480P 视频与音频。同一 4 MiB 范围按一、四、八、四、一连接重复测速，腾讯镜像视频最初约 12–15 MiB/s，重复采样约 39–48 MiB/s；同范围重复请求及远端缓存使结果不能当作持续冷缓存速度。八连接未显示稳定优势。音频在不同来源和采样间约 2–43 MiB/s，初始化段与当前音频缓存一致，仍不能据此声称正在下载的高画质视频来源得到复现。没有替换用户画质、修改 Cookie 或保存签名 URL。

当前低速的高画质同源原因仍未确认。多任务可同时下载保存，但共享带宽，不能宣称此次更新已解决单视频的 CDN 低速。
